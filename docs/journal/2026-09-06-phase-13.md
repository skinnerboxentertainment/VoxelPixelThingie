**What was built.** `demo/shared/gpu-jobs.ts`: a WGSL kernel with one
invocation per LED per bit, reading each bit's presence and color and its
26 emissions, the LED map as a slot-per-LED table, and writing packed RGB;
`createGpuFrames`, `firstDifference`, and the `led-frame-gpu` workload
whose audit is the CPU path. The Three.js demo builds the kernel before
the renderer, runs every present bit's frame in one dispatch on load and
on size change, reports the time in the HUD, and has a job panel that
runs `led-frame-gpu`, `led-frame`, `links`, or `epcis` on the selected bit
through Phase 12's in-process pool with a browser `MemoryStorage`.

**Decisions.**

- Rounding is `floor(x + 0.5)` in the kernel, the CPU's `Math.round` for
  non-negative values, not WGSL's `round`, which is half to even and would
  disagree on every exact half. The random check includes lights at 0.5
  and 0.75, where the two rules part.
- The audit of a GPU frame is the CPU frame. That makes the GPU path a
  second implementation checked against the first on every job, which is
  what an audit should be.
- The GPU spec runs as its own Playwright project on the system Chrome.
  Probed on 2026-09-06: Playwright's bundled Chromium exposes no WebGPU
  adapter headless on this machine, headed and the system Chrome do, and
  SwiftShader flags removed the adapter everywhere. On a runner with no
  adapter the spec skips and says so in its annotations rather than
  claiming a pass.

**Found on the way.** The first run read `gpuInfo` before the kernel had
finished compiling, because the page said ready from its first rendered
frame while the async pipeline build was still pending. The kernel is now
built before the renderer, so ready implies it. A probe on `about:blank`
reported no WebGPU at all, which is the secure-context rule, not the
browser; probes run on a localhost page.

**Not verified here.** CI's runner has no GPU adapter that we know of; the
first CI run of this PR records whether the GPU project ran or skipped.
