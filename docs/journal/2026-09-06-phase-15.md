# 2026-09-06, Phase 15: One durable backend, the twin named

**Merged.** The actor contract on a durable-execution engine run locally
with no account, the kill-and-restart test, the bench, the twin named
(this entry's PR, tickets 15.1 and 15.2). Program 3 ends here.

**The engine.** Chosen by the survey's ranking, not by what was wired in:
durable execution, top tier, an MIT-licensed SDK and a dev server the
test environment downloads and starts itself. Nothing in the contract is
specific to it; `DurableActorPool` is one backend behind Phase 12's
`ActorPool`, and `InProcessPool` stays the reference.

**Oracles, Verified this session, local dev server on this machine.**

| Oracle | Result |
|--------|--------|
| Sixty-four actors, one `links` job each, in-process worker | 64 audits passed in 2.7 s; every ledger has exactly one request, one result, one audit, one reward, actor `actor:durable-test`; a second submission of the same job attaches to the finished workflow and writes nothing; the scene's digest is unchanged |
| The reference scene's live bits as actors, worker in the same process | 485 actors replayed from the folder in 219 ms (27 destroyed bits have no actor); 485 `links` jobs in 15.7 s, all passed; 485 ledgers with exactly one record per step |
| Kill the worker mid-job with SIGKILL, start another | request recorded at +1.0 s, worker killed inside the work step, second worker up, job completed at +19.5 s; the workflow describes as COMPLETED; the ledger holds exactly four records |

**What the engine guarantees, what the ledger guarantees, where they
meet.** The engine guarantees that a started workflow runs to completion
whatever happens to the worker: when the killed worker's heartbeat stops
(3 s), the step is retried on the next worker that polls, with the
workflow's history replayed to that point. The ledger guarantees nothing
about retries by itself; each record step first reads the bit's ledger
from the folder and this session and writes only when its record is
absent. The two meet at the workflow id, `bit-<bit id>-job-<job id>`, with
duplicate ids rejected: a job resubmitted is the same workflow, and a
step retried is the same step against the same ledger. The conditions
relied on: a heartbeat timeout of 3 s and a start-to-close of 60 s; one
scene folder shared by successive workers; ledger appends that are whole
lines. The exactly-once claim is about the ledger's records, which is
what the bit's history is; the engine's own claim about activity
execution is at-least-once, and the idempotent steps are what turn that
into one record.

**What was built.** `scripts/durable/workflows.ts` (the workflow: request,
work, result, audit, reward as activities), `scripts/durable/activities.ts`
(activities over an `ActorHost`, each record step idempotent against the
ledger, a heartbeating `slow` workload for the kill test),
`scripts/actor-durable.ts` (`DurableActorPool` and `createActorWorker`),
`scripts/durable-worker.ts` (a worker over a scene folder),
`bench/durable.bench.ts`, and `performJob` extracted from the in-process
pool so both backends run the same work-and-audit step. ADR 0009 names
the simulator the physical bit's digital twin in the original sense and
cites the Phase 10 numbers under that name.

**Found on the way.** The workflow path was built from a URL's pathname
and carried a `%20` for the space in the workspace folder; the worker's
bundler could not find it. `fileURLToPath` is the right call. And a
stash-and-merge to bring the branch level with main dropped the untracked
files with the stash; the dropped stash's third parent still held them and
`git fsck` found it.

**Not done.** No hosted backend and no account, by design; the survey
ranks the options if one is ever wanted. The token layer stays out.

**Program 3, closed.** Identity with recourse (Phase 11), work as audited
events (12), local compute first (13), the scene as an MCP server (14),
one durable backend (15). Open on the board: the hardware tickets #72 and
#73, and release 0.4.0 held for first light.
