**What was built.**

- `src/led-map.ts`: `vpb-led-map/1`, a strip length and one LED range per
  slot, validated for overlap and overrun; the default is the plan's
  68-LED strip. `ledFrame` turns a `BitRecord` into RGB bytes: emissions,
  not the culled render list, because a cube on a desk is seen from every
  side; an absent bit is dark. The map rides in the passport under
  `ledMap` (SPEC.md §9.5), so a physical bit carries its own wiring.
- `src/ddp.ts`: the ten-byte header exactly as the specification and
  WLED's receive path read it, encode and decode, frames split at 1,440
  data bytes with push on the last packet.
- `scripts/led-bridge.ts` and `scripts/led-drive.ts`: a UDP sender with a
  running sequence, a scene mode that lights one bit from a folder or a
  pack, and an HTTP bridge the browser posts to, since a page cannot open
  a UDP socket. Every post is timed from the demo's event time.
- The Three.js demo takes `?led=<bridge>&bit=<id|first>` and tees the
  bit's events to the bridge; autosave keeps the tee.
- `demo/passport/`: one bit by id from a published scene, read as two
  files (`passport.json`, `events.jsonl`) rather than a replay, with a QR
  code of the page's own address. The default scene is the GitHub mirror
  of the reference scene, which serves `Access-Control-Allow-Origin: *`.

**Decisions.** ADR 0009: DDP over Art-Net and E1.31 for the smallest
header and no universe arithmetic; the map is data in the passport, not
code; browsers post, Node sends. The QR library is `qrcode`, a
devDependency bundled into the page, rather than an encoder of our own.

**Bugs found on the way.**

- The bridge's URL parameter was read after the first scene was built,
  so the sink never attached; the e2e test caught it on its first run.
- A hand-written expected packet had the data-type byte wrong; the test
  said `0b`, and `0b` is what WLED defines. The test was corrected, not
  the code.
- CI's first run failed the Phase 8 save gate at 3,960 ms against 3,000:
  the new LED spec and the save spec ran in parallel on the runner's two
  workers, both driving WebGL. Playwright now uses one worker on CI, so
  timing gates measure the runner, not the neighbor.

**Addendum, later the same day: the simulated physical bit (#76).**

Oscar: "for the time being, we'd have to simulate the physical and marry
it to our platform." Discussed and planned before a line was written; the
decisions were a fuller WLED emulator, terminal only, faithful in push and
timeout, with the measurement extended to the terminal write.

What was built: `scripts/wled-sim.ts`, a WLED emulator that takes real DDP
with WLED's receive rules (read from wled00/e131.cpp, udp.cpp, json.cpp,
cfg.cpp, wled.h, FX.h), keeps its realtime timeout, brightness scaling,
live override, and idle color, and answers `/json/info`, `/json/state`,
`/json`, `/json/si`, `POST /json/state`, `/json/cfg`, plus `/vpb/stats`;
`scripts/cube-net.ts`, an unfolded-cube terminal view whose cells come from
slot geometry, so each edge sits on two tiles and each corner on three by
construction; a send queue and sequence-stamped samples in the bridge; a
JSON API probe in the driver; and a cross-process end-to-end test with the
simulator as its own child process. ADR 0009 is amended.

The metric is **click→terminal-write**: the demo's event time to the moment
the frame's bytes are accepted by the output. Terminal compositing is not
in it, and the number is not click→photon. Against PLAN-2's "within one
frame", a p95 of 17 ms sits inside a 33 ms frame with room for the strip.

**Found on the way.**

- Windows loopback UDP delivered the first packet after the second in
  three runs of three. A join by arrival order mis-paired everything
  after it and reported two seconds of latency; the join now pairs each
  frame with the latest send of the same DDP sequence that left before
  the frame's packet arrived, which survives reordering and coalescing.
- The simulator coalesces like WLED, one show per 15 ms, so 121 sends
  became 103 frames; and the page's setup outlasts the test's 1.5 s
  timeout between the seed packets and the changes, so the simulator went
  idle and re-entered live, blanking the strip, exactly as the device
  would. The test asserts `live` while packets flow, not after setup.
- The renderer's edge cells first mapped to LEDs 1 and 2 only; the test
  for "each edge shows its whole range" caught it.

**Not verified here.** The live terminal path (alternate screen, hidden
cursor, resize, Ctrl-C restore) was exercised only through an injected
stream in a unit test; this session has no TTY. The first real run is
Oscar's: `node --experimental-strip-types scripts/wled-sim.ts` in Windows
Terminal, then `npm run led:drive -- --scene <pack> --http-port 8790`.
